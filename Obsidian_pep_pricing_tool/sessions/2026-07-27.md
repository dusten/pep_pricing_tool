# Session 2026-07-27

## Emoji "obj" box bug: fixed a real latent bug, diagnosed the actual report to a client-side source

User reported that pasting emoji into the admin "Add Vendor" shipping-note textarea showed broken
box glyphs (example given: `✈️ Regarding shipping / ⏱️ 7-10 business days / 💰 Up to 1-6BOX: $70`).

**Found and fixed a real bug while investigating**, unrelated to the report's actual cause: the
Fraunces display font added in the 2026-07-23 design pass (`main.css`) had no `unicode-range`
descriptor on its `@font-face`. Per spec, that makes the browser treat the font as claiming *every*
Unicode codepoint (default range is the whole of Unicode), so any character Fraunces doesn't
actually have a glyph for — including emoji, and any non-Latin text — renders as tofu instead of
falling through to the next font in the stack (Georgia/serif). This would have silently broken, e.g.,
a vendor/user display name containing an emoji rendered in the Dashboard welcome heading (which uses
`--font-display`). Fixed by adding an explicit `unicode-range` restricted to the Latin ranges the
font file actually contains (same ranges Google's own served CSS uses for the latin subset). Also
hardened `--font-sans` with explicit emoji-font fallbacks (`Apple Color Emoji`, `Segoe UI Emoji`,
`Noto Color Emoji`) as cheap additional insurance.

**But** that fix doesn't touch the actual reported field — the shipping-note textarea is a plain
`<textarea>` with `font-family: inherit`, nowhere near `--font-display`. Reproduced the report
directly: typed the exact emoji text live into that exact field on the real site — real color emoji
rendered correctly, no tofu. Checked for a custom paste handler on that field (there's a `@paste`
handler in this same file, but it's scoped to a separate `.paste-zone` div used only for
screenshot-to-file-upload, not the shipping textarea) — ruled out.

Asked the user where the text was copied from: **WhatsApp**. This nails the actual cause — WhatsApp
Web renders emoji as image sprites rather than relying on the OS's Unicode emoji font, and copying
text containing them can leave behind U+FFFC (the OBJECT REPLACEMENT CHARACTER, literally what some
fonts/browsers show as a box containing the text "obj" — matching the report precisely) instead of
the real emoji codepoint. A plain `<textarea>` can only ever receive plain text on paste; if the
source's plain-text clipboard payload is U+FFFC, the actual glyph data was never there to recover —
no CSS or font fix on our end can fix this, since it isn't a rendering bug, it's genuinely missing
data.

**Shipped anyway**, since vendor onboarding explicitly involves pasting vendor-supplied text and
WhatsApp is a very plausible common source: `VendorsTab.vue`'s `save()` now strips U+FFFC from
`shipping_note` and `notes` before the API call (`stripObjectChar`), so the artifact doesn't get
saved as visible garbage even when a real emoji couldn't be recovered from the paste. Verified the
regex logic directly (real emoji left untouched, U+FFFC instances removed) rather than creating a
throwaway vendor in the real DB just to exercise a pure string function.

`bash deploy.sh` × 2 (font fix, then the strip fix) both passed smoke checks.

## Tablet-form product tracking (is_tablet flag, mirrors is_raw_material)

User kept running into vendors selling tablet/oral forms and asked how to track them, floating
"maybe a different table." Investigated the existing `pc_products`/`pc_specifications`/`pc_prices`
schema first rather than assuming a new table was needed — `is_raw_material` already solves the
identical problem ("one product, more than one form, needs its own filter+badge in the comparison
grid, no changes to the $/unit math"), so a new `is_tablet` boolean on `pc_specifications` mirroring
`is_raw_material` end-to-end was the right, much smaller scope. Confirmed via AskUserQuestion before
building: mix of same-compound-different-form and tablet-only products, full price-comparison
integration wanted (not just lightweight tagging), pricing convention (per-tablet dose vs. per-bottle-
only) still unknown/varies by vendor.

Delegated the build to a Sonnet 5 subagent with a fully-specified prompt covering every touch point
`is_raw_material` already has (migration, `findOrCreateSpec()`, the extraction prompt, comparison
filters, Comparison page checkbox+badge, Review Queue checkbox, exports, admin query-log rerun) —
after pre-identifying a subtle correctness requirement myself first: the unique key has to widen to
`(product_id, spec_label, is_tablet)`, and BOTH spec-lookup queries (`findOrCreateSpec()` and
`pending_imports.php`'s separate auto-approve-matching-vendor `$specCheck` query) must filter on
`is_tablet`, not just `spec_label` — unlike raw-material's "1g" label, which never collides with a
finished dose, a tablet dose plausibly shares the exact same label as an injectable dose of the same
product (both "5mg"). Without both fixes, a same-labeled tablet/vial pair would either fail to be
created as a distinct row, or silently reuse the wrong existing spec.

**Migration 041** (`pc_specifications` gains `is_tablet BOOLEAN DEFAULT FALSE`, unique key widened),
**claude.php** rule 13 (oral tablet detection, `kit_vial_count` = tablet count per bottle, falls back
to `spec_label="1 tablet"` + a warning when no per-tablet dose is stated at all), **Comparison page**
(new "Tablets only" checkbox mirroring "Raw/bulk powder only", a `badge-advanced` "Tablet" badge next
to the spec label in both table and list views), **Review Queue** (matching checkbox for admin
correction). Explicitly left `vendor_suggestions.php`'s strict-template CSV parser untouched — it
doesn't support `is_raw_material` either today, extending it would be new scope beyond matching the
existing precedent.

**Independently verified before pushing** rather than trusting the agent's report at face value:
read the actual diff for both correctness-critical lookups (both fixed correctly — `findOrCreateSpec()`
now filters `is_tablet = ?` in its SELECT, and `pending_imports.php`'s `$specCheck` query does too),
grepped for every remaining call site of `findOrCreateSpec()` to confirm none were missed, confirmed
`commitExtractionResult()` (shared by both the vendor-file and vendor-suggestion accept flows) can't
bypass the fix since it only ever writes through `pc_pending_imports` → the same approve endpoint,
re-ran `SHOW CREATE TABLE pc_specifications` myself against production to confirm the live schema
matched, and independently confirmed the agent's own throwaway test data (product/vendor/specs/prices)
was actually gone via direct SQL. `bash deploy.sh --sync-schema` smoke-checked clean. Pushed as `2b352bd`.

## Review Queue: real product picker, auto-commit low-risk new_spec rows, CJC-1295 DAC watchlist

Same session, immediately after the tablet feature, the user raised two connected pain points: 111
items sitting in the admin Review Queue, and a specific recurring identity mismatch — vendor listings
for "CJC-1295 with DAC" kept getting suggested against the existing-but-wrong "CJC-1295 without DAC"
product (a genuinely different compound — DAC is a Drug Affinity Complex modification that changes
the half-life from ~30 minutes to about a week, not a spelling variant of the same thing) — forcing
the user to just skip the row every time, since the review card offered no way to map onto a
*different* specific existing product.

**Root-caused with real data** before proposing anything: queried the live `pc_pending_imports`
breakdown (`new_product` 30 / `new_spec` 31 / `name_mismatch` 46 / `incomplete_spec` 4) and traced the
CJC mismatch to a real, measurable imbalance — "CJC-1295 without DAC" had accumulated 11 alias
spellings over time (people correcting vendor listings into it repeatedly) while "CJC-1295 with DAC"
had only 1. The candidate-suggestion logic (`findFuzzyProductCandidate()`) is pure Levenshtein
distance across every product+alias with no domain awareness — 11x more spelling variants to compare
against meant "without DAC" won the distance comparison almost by default for any novel vendor
phrasing, regardless of which one was actually correct. Neither name was on the existing
variant-compound watchlist either, which already exists for exactly this class of problem
(Epithalon/TB-500 pairs) but had never been extended to cover CJC-1295.

**Fixed the data imbalance directly myself** (kept tight control over this one, rather than delegating
a data-content decision): backfilled 5 more realistic alias spellings for "CJC-1295 with DAC"
(product 59) via direct SQL — `CJC-1295 DAC`, `CJC1295 DAC`, `CJC-1295(DAC)`, `CJC 1295 (with DAC)`,
`CJC-1295 带 DAC` (Chinese, mirroring an existing Chinese alias already on the without-DAC side) —
closing the imbalance to 7-vs-11.

**Delegated the code changes** to a Sonnet 5 subagent, confirmed via user sign-off on all three
proposed fixes before building:
1. Added CJC-1295 with/without-DAC to `VARIANT_COMPOUND_WATCH_NAMES` in `claude.php`.
2. Replaced the Review Queue's "map onto the one suggested candidate" checkbox — which defaulted to
   *checked*, meaning the only genuinely safe option was to skip the row entirely — with a real
   search+select over the full ~286-product catalog, defaulting safely to create-new. The suggested
   candidate is now only offered as an explicit opt-in button, never pre-selected. Backend gained a
   `create_new` flag on the approve endpoint, since previously omitting `product_id` still silently
   fell back to the stored `candidate_product_id` — there was genuinely no way to force "create new"
   once any candidate existed.
3. `vendor_file_processor.php`: once `findExactProductMatch()` succeeds, a spec that doesn't exist yet
   on that already-confirmed product no longer gets parked as `new_spec` for review — product
   identity isn't in question there (only `new_product`/`name_mismatch` carry real identity risk), so
   it now auto-commits straight through `findOrCreateSpec()`/`commitPriceRow()`.
4. A one-off backfill script (`migration_scripts/2026-07-27-backfill_new_spec_auto_commit.php`) cleared
   the 31 pre-existing `new_spec` rows the same way, run for real against production.

**Independently verified before considering this done**: read the actual diff for all three PHP
changes (the `$forceNewProduct` short-circuit, the `findOrCreateSpec()` auto-commit replacing the old
pending-insert branch, the watchlist array) and the Vue picker's template/script changes. Re-ran the
pending-imports breakdown myself against production — `new_spec` gone entirely, `new_product`/
`name_mismatch`/`incomplete_spec` unchanged at 30/46/4 exactly as expected (confirming the fix touched
only what it should have). Confirmed the CJC watchlist text is genuinely live by grepping the deployed
`claude.php` directly over SSH rather than trusting the report. Confirmed the agent's own throwaway
test product and admin session were actually cleaned up via direct SQL. `bash deploy.sh` smoke-checked
clean. Pushed as `2c98b85`.
