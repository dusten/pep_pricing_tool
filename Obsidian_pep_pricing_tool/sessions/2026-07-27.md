# Session 2026-07-27

## Emoji "obj" box bug: fixed a real latent bug, diagnosed the actual report to a client-side source

User reported that pasting emoji into the admin "Add Vendor" shipping-note textarea showed broken
box glyphs (example given: `✈️ Regarding shipping / ⏱️ 7-10 business days / 💰 Up to 1-6BOX: $70`).

**Found and fixed a real bug while investigating**, unrelated to the report's actual cause: the
Fraunces display font added in the 2026-07-23 design pass (`main.css`) had no `unicode-range`
descriptor on its `@font-face`. Per spec, that makes the browser treat the font as claiming *every*
Unicode codepoint (default range is the whole of Unicode), so any character Fraunces doesn't
actually have a glyph for — including emoji, and any non-Latin text — renders as tofu instead of
falling through to the next font in the stack (Georgia/serif). This would have silently broken, e.g.,
a vendor/user display name containing an emoji rendered in the Dashboard welcome heading (which uses
`--font-display`). Fixed by adding an explicit `unicode-range` restricted to the Latin ranges the
font file actually contains (same ranges Google's own served CSS uses for the latin subset). Also
hardened `--font-sans` with explicit emoji-font fallbacks (`Apple Color Emoji`, `Segoe UI Emoji`,
`Noto Color Emoji`) as cheap additional insurance.

**But** that fix doesn't touch the actual reported field — the shipping-note textarea is a plain
`<textarea>` with `font-family: inherit`, nowhere near `--font-display`. Reproduced the report
directly: typed the exact emoji text live into that exact field on the real site — real color emoji
rendered correctly, no tofu. Checked for a custom paste handler on that field (there's a `@paste`
handler in this same file, but it's scoped to a separate `.paste-zone` div used only for
screenshot-to-file-upload, not the shipping textarea) — ruled out.

Asked the user where the text was copied from: **WhatsApp**. This nails the actual cause — WhatsApp
Web renders emoji as image sprites rather than relying on the OS's Unicode emoji font, and copying
text containing them can leave behind U+FFFC (the OBJECT REPLACEMENT CHARACTER, literally what some
fonts/browsers show as a box containing the text "obj" — matching the report precisely) instead of
the real emoji codepoint. A plain `<textarea>` can only ever receive plain text on paste; if the
source's plain-text clipboard payload is U+FFFC, the actual glyph data was never there to recover —
no CSS or font fix on our end can fix this, since it isn't a rendering bug, it's genuinely missing
data.

**Shipped anyway**, since vendor onboarding explicitly involves pasting vendor-supplied text and
WhatsApp is a very plausible common source: `VendorsTab.vue`'s `save()` now strips U+FFFC from
`shipping_note` and `notes` before the API call (`stripObjectChar`), so the artifact doesn't get
saved as visible garbage even when a real emoji couldn't be recovered from the paste. Verified the
regex logic directly (real emoji left untouched, U+FFFC instances removed) rather than creating a
throwaway vendor in the real DB just to exercise a pure string function.

`bash deploy.sh` × 2 (font fix, then the strip fix) both passed smoke checks.
