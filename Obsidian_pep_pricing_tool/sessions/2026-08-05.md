# Session 2026-08-05

## Inventory tab: relabel a mislabeled dose on one price row (10mg → 15mg fix)

User needed to correct a specific vendor's price line where the vendor had mislabeled the dose
(Premipeptides' "Tesamorelin + Ipamorelin combo" listed as 10mg, actually 15mg). No existing
capability could do this — `PUT /api/prices/{id}` (Inventory tab's edit form) explicitly could not
reassign which spec a row belongs to; only `products/spec_move.php` existed, and that moves a whole
spec (every vendor's prices under it) to a different *product*, not one vendor's one row to a
different *spec* on the same product. Found the real target row via direct SQL first (vendor 10,
product 312, spec 1023/"10mg", price_id 5113) and confirmed a "15mg" spec (id 1375) already existed
on that product from other vendors — so the fix needed to *repoint* onto the existing spec, not
create a duplicate.

Built the capability rather than just hand-fixing the one row, since the underlying gap (no way to
correct a mislabeled spec at all) would recur. `prices/update.php` gained optional
`spec_label`/`numeric_value`/`unit`/`is_raw_material`/`is_tablet` fields, resolved via the same
`findOrCreateSpec()` every import path already uses — repoints onto an existing sibling spec on the
product if the label matches one (the common case, exactly this scenario), or creates a new spec
otherwise. Moved the spec resolution to run *before* the existing price_per_unit computation, since a
pure relabel (same price/kit) still needs $/unit recomputed against the corrected dose — extended
that computation's trigger condition accordingly. Deliberately did NOT log a `pc_price_history` event
for a pure relabel with no price/kit change (it's a data-correctness fix — "this was always 15mg" —
not a real price-change event that belongs on the Calendar). `vendors/show.php` (which feeds the
Inventory tab) now also selects `numeric_value`/`unit`/`is_raw_material`/`is_tablet` per row so the
frontend can pre-fill and preserve them.

Frontend: the Spec column in `InventoryTab.vue` changed from plain read-only text to three small
inputs (value/unit/label), matching every other directly-editable field in that table — editing the
value/label and blurring triggers the same `save()` used everywhere else, which now always includes
the spec fields (a no-op re-resolution in the common case; only actually repoints the row if the
admin changed them) and patches the row from the server's authoritative resolution afterward rather
than trusting its own typed input.

**Verified against a throwaway vendor+row before touching real data**: confirmed a relabel from
10mg→15mg correctly repointed onto the existing sibling spec (not a duplicate), recomputed
`price_per_unit` correctly, and logged zero `pc_price_history` rows (pure relabel, no price change).
Separately confirmed the collision-safety path: attempted a relabel that would collide with another
existing row for the same vendor at the target spec/tier/SKU — got a clean 409 error instead of a raw
SQL crash, and confirmed the row was left completely untouched (atomic UPDATE, no partial state). All
throwaway data deleted and confirmed gone before proceeding.

**Applied the fix to the real row** (price_id 5113) via the newly-verified endpoint: Premipeptides'
"Tesamorelin + Ipamorelin combo" now correctly shows 15mg / $60.00 / $0.36 per unit, repointed onto
the same spec other vendors already use for the real 15mg dose. No price-history event was logged
(correct — not a real price change). Confirmed live in the actual Inventory tab in the browser.
`bash deploy.sh` smoke-checked clean, `php -l` clean on both touched backend files, zero console
errors.
